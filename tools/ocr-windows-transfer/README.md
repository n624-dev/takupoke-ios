# Windows OCR候補のApple環境での比較

独立した架空の画像PDFを使う、認識器だけの比較。アプリの改善・配信モデルの
品質合格を先に宣言しない。アプリ本体、Strictとそこへ至る経路、Parser33／32、
Validator、0.85の条件、本文最大3項目の訂正は変更しない。

## 固定した入力と比較

`protocol.json`で生成seed・モデルと辞書のimmutable URL／サイズ／SHA・字体・
文字サイズ・全比較条件を固定する。KaiseiOptiとZenKakuGothicAntiqueはWindowsで
使用済みの字体であり、未知書体・学習との完全な非重複は主張しない。
学校資料やその名前を置換した入力は使用しない。

各字体72項目、計144項目。英数字コード、英字のみ、数字のみ、架空の日本語本文・
異体字を含む本文・英語本文を各12項目ずつ、24／32／40pxで描く。
元PNGだけを埋め込んだ6ページPDFを、アプリと同じCropBox・最大2倍・2048px以内の
PDFKit thumbnail条件でApple環境に取得させる。

ページ全体の既定Documents認識と、同じ原画素の物理セル内側／観測したinkの周囲2pxの
2条件を比較する。切り抜き領域は生成器が既知の物理罫線から与えるため、この実験は
アプリがセル・本文所属を証明できたという根拠にはならない。
inkはRGBの最小値250未満の実画素から決め、認識文字や正解で範囲を選ばない。

局所比較はVision既定Documents、accurate Text、Windowsの日本語V6・英数字v1・
コード用V3・日本語V3。全条件を実行し、正解から都合のよいモデルを選ばない。
ONNXはFP32の固定モデル・CPU Runtime1.23.2・BGR／48px・丸めたuint8 bilinear・
正規化後ゼロ余白・元の辞書とgreedy CTCを使う。全CTC文字と時間範囲・確率・
reject値・余白の支持状態を保持する。Windowsの検出・切り替え・正式採用全体の
再現試験とは区別する。

## 評価と次段階の条件

正解は`oracle.json`へ分離し、PDF／画像の生成後、全認識の完了後だけ比較器が読む。
全体、字体、分類ごとの完全一致、文字距離、既定ページ認識からの改善／悪化、
各経路自身の高スコア誤読、欠落／分割と実呼出し数を報告する。
Visionの行が複数・未取得・領域外の場合は未所属文字列として文字距離にも計上する。
文字の正しさと所属成功を区別する。

各APIとモデルのスコアは同じ尺度ではない。一致・高スコア・この比較の成功を
正しさや正式採用の証明へ転用しない。CPUモデルのpeak RSSはそのPythonプロセスだけで、
アプリ全体やiPhoneの使用量ではない。

この比較が完了しても追加Manifestは空を維持する。効果のある候補について、iOS自身の
Runtime、独立した文書全体、既存正解の維持、否定例、本文3項目以内の確認、
メモリ・取消・原本保持を確認してからOCR専用経路への接続を判断する。
全13配布チェックと同一ソースの配布物照合も必要で、実機は別確認とする。

## 実行

Actions開始前には開発規約どおり新規GPT-6.1 Sol／Highで対象コード差分をレビューする。
専用workflowは開発ブランチの比較コード変更で実行する。学校サーバーへ接続せず、モデル／字体の
取得と認識処理を分離する。結果は完全架空の数値・生認識記録だけをログに出し、
cache／artifactを作らない。所有するPDF・画像・モデル・依存・module cacheは終了時に削除する。

```bash
bash tools/ocr-windows-transfer/run.sh
```

比較器の実行成功は認識精度の合格ではない。実測は`docs/ocr-improvement-log.md`と
`docs/verification.md`へ記録し、この手順へ進捗を混ぜない。
