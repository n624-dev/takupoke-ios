# 端末内SQLite保存・時間割統合の設計案

[READMEに戻る](../README.md)

状態：SQLiteへの通常保存・読出しを実装済み。採用版を履歴として保存する設計は未実装。週の表示上の統合は[時間割タブの仕様](timetable-tab.md)を参照。旧JSONからの移行処理は接続していない。
以下は保存モデルの設計資料である。「採用方針」「実装案」「確認待ち」を区別し、未確定の項目を実装済みの仕様として扱わない。

## 採用方針

SQLiteで原本の来歴、解析結果、採用する入力の組み合わせを分離する。DB化の目的は資料間の関係・適用範囲・制約を管理すること。現行JSONにも原子的保存と失敗時の保持があり、その保護を引き継ぐ。

- 解析成功、日付への適用可否、更新確認、変更の解決状態を別々に記録する。
- 更新に失敗しても前回結果を保持する。保持していることを、最新・適用可能の根拠にしない。
- 適用期間外の通常時間割を現在の予定へ流用しない。基本時間割の欠落と、根拠のある「授業なし」を区別する。
- 原本と解析結果を版単位で保持する。保持中の内容は別内容へ上書きしないが、全履歴の永久保存は行わない。
- 採用版は解析結果と適用期間などの組み合わせを表し、全授業を毎回複製しない。
- 資料全体の読み取り失敗と、読み取った変更の対象を決められない問題を区別する。後者は出典と未確定状態を残す。
- 名称表示だけの対応表がなくても原資料の記載名を使える。照合に対応表が必要な場合は、表示だけの不足と区別する。

診断データ・学校資料・端末DBはリモートへ送信しない。設計・公開テストには独立した架空例だけを用いる。学校行事の取得・解析・タグ・表示は、既存の凍結方針を維持し、未定のAPIへ先行移行しない。

## 現行モデルから引き継ぐ情報

| 現行コード | モデルの拡張・保持の要点 |
| --- | --- |
| `MaterialLibraryState` / `MaterialRecord` | 現在は資料種別ごとに1件。資料の取得元と原本の版を分け、複数の通常時間割を参照できる構造へ拡張する |
| `MaterialSource` | ブックマーク、取得先、ETag等を端末内に保持。原本の内容と取得元の設定を同一視しない |
| `PDFAnalysis` | 原本ハッシュ・解析器版・年度・学期・原文・ページ等を維持。年度・学期ラベルから適用日を推測しない |
| `PDFLesson` | 同一クラス・曜日・時限の複数授業を許す。記載名と正式名称を維持 |
| `ChangeAnalysis` | 原本ハッシュ・解析器版・補完年を引き継ぐ。補完年変更は別の解析条件 |
| `ScheduleChange` | 時限は文字列。教員・教室はそれぞれ単一値。元行番号、変更前後の教員・教室は現状では取得していない |
| 取得・解析の試行記録 | 成功結果から分離して保持。失敗を空の正常結果へ変換しない |
| 警告確認後のプレビュー | 閲覧専用のままとし、正常解析や採用結果へ昇格させない |

DBで保持する解析の元ファイルが失われても、ハッシュと出典を保持する。現在取得済みの別原本へ付け替えない。元行番号が不明なら不明のまま保存し、配列の番号をExcelの行番号として扱わない。これはDB内の保持規則であり、開発版の旧JSON引き継ぎを要求するものではない。

## データの関係の実装案

以下は論理的な単位であり、テーブル数・SQL定義の確定ではない。

| 単位 | 主な内容・関係 |
| --- | --- |
| 取得元 | 種別、取得設定、要求世代。複数の原本版を取得できる |
| 原本版 | 種別、ハッシュ、サイズ、元の名前、取得日時、元ファイル更新日時、管理ファイル参照。実体の存在状態は内容と別管理 |
| 試行 | 対象取得元・原本・要求世代、操作種別、開始／終了、成功／失敗／中断。取得確認と解析完了を区別 |
| 解析版 | 原本版、解析器の種類・版、入力条件、完了日時、構造検証結果。完成後の行は不変 |
| 解析行 | 通常授業・変更等の検索用項目と原文・出典。行のIDは照合根拠の代わりにならない |
| 適用範囲 | 期間、対象クラス等、範囲の根拠、完全一覧／期間限定一覧／差分という契約。解析で判明した範囲と利用者指定を識別 |
| 採用版と入力参照 | 解析版、役割、適用範囲、結果に影響する設定・統合規則。前期・後期など複数の基本時間割を参照可能 |
| 統合問題 | 対象日・クラス・時限等の分かる範囲、原因、出典、候補。範囲自体が不明な問題も記録可能 |
| 現在の採用参照 | 検証済み採用版を指す。切替はトランザクションで行う |
| 保持理由 | 採用中、復旧用、次期利用、処理中、閲覧中、バックアップ中などの参照 |

解析結果の再利用キーは「原本の内容＋解析器の種類・版＋結果に影響する全入力条件」。補完年を含み、照合・解析へ影響する対応表を導入した場合はその内容の識別子も含める。単に表示するクラスや画面設定まで一律に版管理しない。

日付は学校の暦上の日付として扱い、取得・解析の日時と別の型にする。実際の授業日と基本時間割の参照曜日も分ける。期間の境界は内部では開始日を含み終了境界を含まない形式を候補とし、資料の「最終日」を保存する場合は変換を明示する。タイムゾーンや年度境界を端末の現在設定・現在年から暗黙補完しない。

## 状態と禁止事項

| 独立した状態 | 保存・判定する内容 |
| --- | --- |
| 読み取り | 未実行、実行中、成功、失敗、中断。正常0件と非0件も区別可能にする |
| 適用 | 期間・対象が確認済み、未確認、対象外 |
| 更新確認 | 対象取得元・確認時点・結果。確認成功を、その後も最新である保証としない |
| 統合 | 対象が一意、根拠のある授業なし、対象不明・競合、必要な入力の不足 |
| 原本の利用可能性 | 存在、欠損、一時的アクセス不能。ロック中の不能を欠損や破損としない |

禁止する状態と、守る場所を先に定義する。

| 禁止する状態 | 制約・処理の案 |
| --- | --- |
| 解析途中・警告プレビューが正常な採用入力になる | 完了・検証状態を採用処理が検査し、解析行登録はトランザクション単位 |
| 学校行事の解析版を通常時間割の役割で参照する | 種別を含む参照制約と採用時の役割検証 |
| 補完年や解析器版が違う結果を同一として再利用する | 再利用キーと保存条件を一致させる |
| 同じ時限の複数授業を一意制約で消す | 授業IDを主キーとし、クラス・曜日・時限は非一意の検索索引 |
| 適用期間が未確認なのに現在の確定予定へ使用する | 適用範囲の検証を統合前に行う |
| 同一範囲の複数基本時間割を根拠なく優先選択する | 範囲競合を検出。優先規則が確定するまでは自動選択しない |
| 対象を一意に決められない変更を任意の授業へ適用する | 候補と原文を保存し、確定結果にしない |
| 古い要求の結果が新しい採用状態を上書きする | 要求世代・入力参照・設定を採用直前に比較する |
| 異なる採用版の通常時間割と変更表を画面で混ぜる | 読み取り単位で採用IDを固定する |
| 参照中の版・原本を削除する | 保持参照と外部キーの検査、回収と利用開始の排他 |
| 切替後のDBが読めず旧JSONへ自動復帰する | 保存先切替状態を確認し、更新を止めてDBを保持する |

外部キー・NOT NULL・CHECK・一意制約は、行単位で表せる不変条件に用いる。期間重複、年度との整合、適用可能性などは専用の検証で補う。IDの存在だけでは採用可能と判定しない。

## 変更表の契約と照合：確認待ち

次の情報を確認してから置換・撤回・照合のSQLと規則を決める。

1. **何を完全に含む一覧か**：対象期間・クラスの根拠と、ファイル更新時の掲載範囲。行の日付の最小・最大値は範囲の証明にならない。
2. **訂正・撤回の表し方**：既存行の削除・上書きか、訂正・取消し行の追加か。差分なら安定した識別・順序の根拠も必要。
3. **0件の意味**：表構造と対象範囲を確認できる正しい0件か、解析できなかっただけか。現行の空結果拒否は、この条件が確定するまで変更しない。
4. **問題の影響範囲**：提案は、範囲を特定できる問題なら当該クラス・日・時限を要確認とし、独立した確定箇所は更新する。資料全体の欠落なら部分採用しない。影響範囲不明の場合の扱いは広い範囲で要確認とする案を含めて確定する。
5. **基本時間割の適用日**：PDF、別資料、利用者指定のどれを根拠にするか。年度・前期／後期という表題だけでは日付を決めない。

例えば「架空科目A→架空科目B」が撤回されることと、架空科目Aが休講になることは別操作。同一枠に架空科目A・Bが並ぶとき、ID順で変更対象を選ばない。「A→B、その後B→C」も、順序付き訂正という根拠がない限り行順で連鎖適用しない。時限文字列の分割や教員・教室による絞り込みも、列の意味が確認できた規則だけを使う。

## 登録・採用の実装案

1. 取得・解析開始時に、取得元、原本、入力条件、要求世代を記録する。処理対象の版を保持対象にする。
2. 通信・ファイル読み取り・解析・統合候補の計算は、長いDBトランザクションの外で行う。
3. 解析全体の構造検証を行い、完成した解析版と行を一括登録する。適用範囲の不明な解析結果も閲覧用には保持できるが、確定予定に採用しない。
4. 採用直前の短いトランザクションで、要求世代と各入力・設定・期待する現在採用IDを再検査する。変更されていたら採用せず、必要な再計算へ回す。
5. 採用入力参照と統合問題を登録し、現在の採用参照を同じトランザクションで切り替える。別資料の更新を取り落とさないよう、競合時は新しい組み合わせから作り直す。
6. 読み取りは1つの採用版に固定し、利用が終わるまで必要な参照を保持する。

古い要求の解析成功を記録することと、それを現在の予定に採用することは別。更新が失敗した場合は試行の失敗だけを記録し、正常解析を空配列へ置き換えない。

## 原本の外部保存と回収の実装案

既存の外部ファイル保存を基本にする。BLOBならDBと同時更新できる利点があるが、既存のファイル操作と50 MiB上限を引き継ぎやすい外部保存を優先する。速度・容量の優位性は未測定。

- 処理固有のステージングへ書き、サイズ・ハッシュ・完了を確認してから管理名の不変ファイルへ配置し、その後DBに登録する。
- 配置後にDB登録が失敗しても採用中ファイルへ上書きしない。所有する未登録ファイルだけを回収対象にする。
- 回収は採用中・復旧用・次期利用・処理中・閲覧中・バックアップ中から必要な参照をたどる。単純に新しい2件だけ残す方式にしない。
- 回収予定の登録、参照の再検査、削除、完了記録を再実行可能にする。回収予定への新規参照は削除処理と排他にし、中断後も参照の再検査から再開する。
- プロセス終了で失われる閲覧保持と、次回起動でも必要な採用・次期利用の保持を分ける。起動時に他処理が使うファイルを一律削除しない。
- 原本の欠損は解析結果の削除理由にしない。既知のハッシュ・来歴と欠損状態を残す。

バックアップ対象の原本集合も保持対象として固定する。DBだけのバックアップと、原本を含めた復旧一式を区別し、完成確認前のコピーは復旧用に採用しない。

## 開発版の保存先切替と復旧の方針

旧JSONの内容を引き継ぐ移行は実装対象外とする。開発版ではSQLiteを新しい保存先として初期化し、必要な資料を再取得・再解析して保存し直す。移行候補のコピー・照合・再開は切替の必須条件にしない。

- DBの通常保存・読み込みを先に実装する。既存の `LegacyDatabaseMigration` はアプリへ接続せず、追加開発も当面行わない。
- 新しい保存領域を用意し、初期化完了を確認してから切り替える。以後の起動で毎回初期化したり、旧JSONを自動的に読み戻したりしない。
- 通常の取得・解析では、正常な結果を検証してから現在の参照を更新する。失敗時に空データで上書きしない。
- 読めないDBやロック中のDBを自動リセットする仕様にはしない。開発用の作り直しと通常のエラー処理を区別する。
- 旧保存領域の削除はこの方針変更では実行しない。切替を実装する際は、アプリ所有の保存領域とFile Provider上の元資料を区別する。

将来、保存形式の更新でデータを引き継ぐ必要が生じた段階で、スキーマ移行・バックアップ・復旧手順を定める。現在の将来形式の読み書き拒否は維持する。

## SQLiteの利用方法・保護

| 候補 | 利点 | 引き受ける負担 |
| --- | --- | --- |
| GRDB | 接続管理・移行・監視などの仕組みを利用できる | 依存の固定・ライセンス・各ビルド環境の確認 |
| SQLite C APIの直接利用 | SQLite以外のライブラリ依存を増やさない | 接続・バインド・エラー処理・移行等を実装し検証する |

**保存基盤にはGRDB 7.11.1をコミット固定で追加した。** 単一のDatabaseQueueを使い、外部キー有効・DELETEジャーナル・同期FULLを設定する。Swift PackageとXcodeで同じリビジョンを参照する。テスト結果と実機での確認範囲は[検証記録](verification.md)に記載する。[GRDB 7.11.1公式README](https://github.com/groue/GRDB.swift/tree/v7.11.1#readme)

SQLite設定は実装時に明示し、外部キー有効化、同期設定、ジャーナル方式を読み戻して検証する。WALを無条件に選ばず、接続方式と対象iOSのSQLite実装を確認する。WALでは本体ファイルだけを複製してバックアップにしない。整合した複製にはBackup API等を用いる。電源断時の保証を設定やファイル配置以上に約束しない。[SQLite WAL](https://sqlite.org/wal.html)、[同期設定](https://sqlite.org/pragma.html#pragma_synchronous)、[Backup API](https://sqlite.org/backup.html)

現行の完全保護とバックアップ除外を維持する方針。DB、付随ファイル、原本、復旧用コピーにも適用されることを実機で検証する。ロック中はアクセス不能として延期し、破損扱いや初期化をしない。バックグラウンド要件が確定するまでは保護を弱めない。

## 日別結果・履歴・通知

現在の採用入力から日別結果を計算する。保存する場合のキーには採用版・実日付・対象クラス等を含め、版の違うキャッシュを使い回さない。正確な過去の表示再現には結果そのもの、または再現可能な処理・入力一式が必要で、規則の番号だけでは保証しない。

表示済み結果・通知内容の履歴をどこまで保存するか、復旧用の版の保存期間、古い予定の通知可否は未確定。初回から全履歴を保存する設計にせず、必要な利用期間と目的を確認して決める。

通知の実装時には採用版から生成する期待する予約とOSの予約を照合する。DBの採用切替と同時に同期が必要な世代を記録し、OSへの反映後に、その世代がまだ現在であることを確認して完了記録する。途中終了・一部失敗・反映中の次の採用では再照合できるようにする。予約済みを配信済みとは扱わず、DBとOSを同一トランザクションに含めたと説明しない。

## 実装前に定める検証条件

公開テストは架空資料のみを使用する。以下は全体の検証計画。保存基盤の確認範囲は末尾と[検証記録](verification.md)に分けて記載し、未実装の採用・切替・通知まで通過したとは扱わない。

| ケース | 検証する結果 |
| --- | --- |
| 取得・解析の途中終了 | 前回解析と現在の採用参照が変わらない |
| 構造検証を通る0件 | 確認済み契約の範囲だけを空の一覧へ更新。未検証の空を採用しない |
| 同一原本・異なる補完年／解析器版 | 別の解析条件として扱い、誤って再利用しない |
| 前期・後期の併存 | 適用日に応じた参照を使い、現在・将来に必要な原本を回収しない |
| 並記授業と曖昧な変更 | 根拠のない授業を変更せず、確定した影響範囲へ問題を表示 |
| 訂正・撤回・休講 | 確認済みの資料契約に従い、撤回を休講として扱わない |
| 古い処理の遅い完了・別資料の同時更新 | 現在の採用結果を古い組み合わせへ戻さない |
| 更新失敗・適用期間外 | 保持と適用を分離し、古い結果を最新の確定予定としない |
| 曜日振替 | 実日付と基本曜日を分離。日付指定変更を実日付へ照合 |
| 原本配置後のDB失敗・回収途中の終了 | 参照中原本を保持し、所有する不要物のみ再開時に回収 |
| 原本欠損・ロック | 解析の来歴を保持。一時的アクセス不能を破損と誤認しない |
| 新DB初期化・保存先切替の中断 | 不完全なDBを使用しない。切替後に旧JSONへ戻らず、次回起動で再初期化しない |
| 新しいDB形式 | 読めないDBを削除・初期化しない |
| 通知同期中の終了 | 未完了状態から再照合し、アプリ所有予約を現在の採用世代に合わせる |

## 実装の順序

1. 変更表の契約、曖昧時の影響範囲、学期の適用日を確認し、上記の検証条件を具体化する。
2. 保存アダプターを検証し、テーブル・制約・状態遷移・新DBへの切替手順を確定する。
3. DBの通常保存・読み込みと、開発版の新DBへの切替を実装する。旧JSONの移行は必須にせず、架空データで中断・復旧・保持を検証する。
4. 確定した規則だけで時間割統合を実装する。学校行事の凍結範囲に触れる接続・仕様変更は別途扱う。
5. 表示・通知・バックグラウンドの段階で、保持する日別結果と通知可否を確定して接続する。

## 現在の実装範囲

`LocalMaterialDatabase` は取得元・原本・解析版・授業行・変更行・取得／解析試行を別テーブルに保存する。主キー・資料種別付き外部キー・不変な解析内容を守る制約を設けた。並記授業を保持し、解析条件に補完年を含める。適用範囲は常に未確認で、採用状態を持たない。学校行事は既存解析の内容をそのまま保存し、意味や処理を変更しない。

以下の移行候補作成は方針変更前の実装で、今後の切替の必須経路にはしない。

`LegacyDatabaseMigration.prepare` は旧領域と重ならない領域に専用候補を作る。原本のコピーとバイト照合、DBへの一括登録、閉じたDBの再読込、参照と件数・内容の照合、処理中に旧データが変わっていないことの確認を行う。失敗時はこの呼出しが作成した候補だけを削除する。旧JSON・原本を書き換えず、既存のファイル回収処理も呼ばない。

旧解析のハッシュに対応する原本が現行保存にない場合は、ファイルを持たない来歴として保存する。現原本に付け替えない。現行レコードが指す原本自体がない場合は、現段階の候補作成を中止して旧データを残す。原本ハッシュは旧JSONから保持するもので、この段階では再計算していない。コピー前後と完了直前のバイト一致は検査する。

候補の再読込APIは旧保存の移行検証専用で、種別ごとの複数解析を自動選択しない。アプリは通常保存用の読出しを使用し、移行候補作成処理を自動起動しない。

### 通常保存と開発版の切替（2026-09-20）

`MaterialWorker.open` は新しい `SchoolMaterialsSQLite` 領域を使う。初回は専用の `.initializing` 領域で空DB・原本置場・ステージングを作り、DBを閉じて再読込できた後にディレクトリ名を切り替える。途中で残った初期化領域は次回の初期化時に回収する。既存領域のDBが欠損・破損・非対応形式なら更新を止め、空DBへ作り直さない。旧 `SchoolMaterials` と元資料は削除しない。

スキーマ2には現在取得済み原本を指す `currentRecord`、最後の正常解析を指す `currentAnalysis`、フォルダと保存世代を持つ `currentLibrary` を追加した。これらは資料一覧・解析閲覧用であり、日付に適用できる時間割の採用参照ではない。解析結果の適用範囲は未確認のまま。既存アプリと同様、種別ごとに最後の正常解析を表示する。

取得では原本ファイルを配置してからDBを更新し、解析では原本ID・解析条件・検索用の行・試行結果・現在の参照を一括登録する。同じハッシュでも、再解析した取得原本のIDへ結び付ける。保存世代が変わった書込みは拒否する。明示的な再解析を記録できるよう解析実行の一意制約には完了時刻も含めるが、結果再利用のキーに時刻を含める設計ではない。再利用キャッシュは未実装。

現在取得済みの原本と最後の正常解析が参照する原本を保持する。取得の更新だけでは正常解析を置き換えない。正常解析の更新後は参照されなくなったDB行を同じトランザクションで整理し、各種別・操作の試行は直近のみを保存する。原本ファイルはPDF閲覧中の可能性があるため即時削除せず、次回の正常読込後に未参照ファイルを回収する。現在の領域はプロセス間の排他ロックで一つの所有者に限定し、別の起動処理がステージングを回収しない。専用領域内の未参照ファイルは再起動まで容量を使う。

この保持規則は現行の資料一覧に限る。今後、採用版・次期時間割・バックアップ等を実装する際には、それらの保持参照も加えてから回収する。初回から全履歴を蓄積する仕様にはしない。

DBの新規作成領域とファイルには完全保護・バックアップ除外、新規配置した原本には完全保護を指定する。取得時の既存SHA-256計算を使い、DB保存時の再計算は追加していない。学校行事の取得・解析・表示規則は変更していない。

残作業：資料契約を確認した採用版・適用範囲・要求世代の設計、時間割統合、その保持対象を含む回収、原本ハッシュ再検証、iOSのファイル保護・ロック中・容量不足・強制終了時の検証。旧JSON移行と順序付きスキーマ移行は当面の必須作業から外す。通常保存の世代チェックは、未実装の採用版の競合解決を代替するものではない。

例外を注入したテストはロールバックと後片付けの検証であり、プロセス強制終了・電源断を再現したものではない。資料契約の確認が必要な時間割統合と、技術上の残作業を分けて進める。
