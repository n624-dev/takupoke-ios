# テスト保守と検証実行の方針

push前は作業差分の `git diff --check` に加え、作成済みコミットにも
`git diff-tree --check HEAD` を実行する。複数の未送信コミットがあれば各コミットを確認する。
作業ツリーがcleanでも、コミット内の末尾空行などは残るためである。
これは内容の検査の代わりではなく、既存CIと同じ差分検査を先に実行する手順である。

変更前にテスト一覧から対象コード・機能・既存ケースを検索する。
新しい仕様や既存ケースで検出できない不具合には、入力と期待結果を追加・更新する。
既存テストで十分なら該当ケース、変更を検出できる理由、実行環境と結果を検証記録へ残し、
不要なテスト編集を行わない。期待値の注入や実装に合わせた期待値だけの変更で通さない。
未登録コード・未登録テスト・対応関係と宣言一覧の不整合はCIで拒否する。
検索一覧は対応関係・宣言名・実行方法が変わったときに更新し、本文のハッシュで更新を強制しない。
宣言数、入力パターン数、実行件数、品質合格を区別する。

UIの変更・実行前には[失敗索引](ui-test-failures.md)を、ケース名・ファイル名・操作・
エラー・対象OSで検索し、関連する詳細記録を読む。
検索語・該当ID・今回比較する条件の違いを検証記録に残す。該当なしも記録する。
失敗したら、対処案や次の実行を決める前に、判明した観測事実を索引へ短く追記する。
ソース・実行／試行・OS／SDK・ケース・失敗段階を残し、原因不明は原因不明と書く。
その後、同じ症状・操作段階・条件を過去の索引と詳細記録から検索し、
当時のコードと今回のコードも照合する。記憶や索引の見出しだけで判定しない。
対処案には過去の失敗済み条件との違いと比較の根拠を記録し、次の試行前にpushする。
失敗した条件を新しい根拠なく再試行せず、候補修正を検証前から解消済みとしない。
異なる条件で同じ症状が再発した事実も残し、個別成功から一般的な解消を断定しない。

テストは件数を一律に削減しない。同じ入力・期待結果・経路を重ねる検査を比較し、
固有の不具合を検出するものを保持する。ロジックはネイティブの動作テストを中心にし、
Pythonのソース文字列検査はそこでしか確認できない生成・登録・ライフサイクル契約に絞る。
内部のguard数などに依存する検査は、可能なものから古い画面操作の拒否等の動作検査へ移す。

大きなUIテストは責務と失敗原因が分かる単位へ整理する。
実タップ・入力・遷移・背景復帰・保存・再起動を通す代表シナリオは維持する。
その他の組合せはロジック検査や短い状態別UIへ移す前に、重複と固有の保証を確認する。
対象は実コントロールと観測した表示領域から決める。固定画面座標、結果・許可の注入、
押し直しによる救済、待機切れの成功扱い、検査条件の緩和は行わない。
操作・照会・スクロール・準備・ビルド・開始待ちを区別して計測する。
操作別の根拠なしに時間短縮率を推定しない。

同じジョブでは同じOS・SDK・構成・生成ソースの準備とビルドを再利用する。
build-for-testingとtest-without-buildingを使用し、失敗したビルドを再利用しない。
異なる構成の成果物を共用しない。ジョブ間のキャッシュ・保存用artifactは使用しない。
所有する一時領域とSimulatorを終了・失敗時に回収する。
重いケースを単純に直列化せず、整理後の実測からジョブ数と割り振りを決める。

開発中のPython・Swift検査と関連UI、配布前の包括的検査は段階的に分ける。
OS依存は両OSで検証し、影響範囲不明なら全体を実行する。
通知停止の切り分けはまずiOS27だけを実行する。通常UIの配布前検証は
27A成功後に26A、27B成功後に26Bを開始し、A・Bは互いに待たず並行する。
失敗した27の系統では対応26を開始しない。手動訂正の26側は、27の通常A・Bと
27の手動訂正4ケース（従来3ケースと明示選択訂正）がすべて成功してから開始する。
従来の13必須チェックを残し、明示選択の両OSを加えた15件すべてを配布条件にする。
配布前には全UI・文字サイズ・VoiceOverを含む必須検証を維持し、
同じコミット・実行ID・試行の成功を公開ゲートで確認する。
軽い開発検証だけで公開しない。mainへのpushによる現行配布経路は、
開発用CIと公開ゲートの設計・検証が終わるまで変更しない。
定期検証とソース加工の縮小は後続の検討とする。

GitHub呼出しは最小限にし、Actions状態はジョブの開始時刻と過去の所要時間から次の確認時刻を決める。
利用者の2026-10-15の追加指示に従い、固定2分間隔の監視は行わない。
複数実行の状態はまとめて確認し、完了済み実行と同じ状態の反復取得を避ける。
新しい完了・失敗を観測したジョブのログを取得する。
Actionsは失敗後もキャンセルせず、残りの結果を確認する。
以前のpendingや公開不可の実行を中止できる許可は撤回済み。
依存関係による未実行は成功として扱わず、自動cancel-in-progressを有効にしない。

Actions開始前（pushによる自動実行を含む）には、最大1つの
GPT-6.1 Sol／Highサブエージェントを毎回新規作成し、実行対象のコード差分だけを渡す。
過去のレビューを担当したエージェントは使い回さない。
意図外の実装、検証の弱体化、期待値の注入を確認させ、指摘を主担当が
確認・修正し、修正差分も確認してから開始する。実装・テスト実行は主担当が行う。

最初の改修対象は、一律テスト編集義務の撤廃、手動訂正UIの整理、
同じジョブ内の準備・ビルド再利用とする。
失敗の調査と修正を並行し、検査を省いて成功として記録しない。
実装・計測の結果はこの方針へ混ぜず、それぞれの検証記録へ残す。
