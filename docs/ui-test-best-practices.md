# UIテスト実装の注意点

UI編集前に読む。詳細・未確定事項は[失敗索引](ui-test-failures.md)と当時のコードで確認する。

- 本番Swiftだけを構文検査する → 生成器による置換後のSwiftも確認する。fixture日付や状態を参照する式を型やmacroの初期値へ移したときは、生成された式のMainActor境界を型検査する。（N143、#122）
- UIKitを含む画像検査を構文parseだけで渡す → 色の計算や画素集計は実Swiftの式をLinuxで型検査して架空配列で実行する。製品の色定数チェックに加え、意図した線と背景をAppleの実画像で確認し、判定の前に診断画像を保存する。実機の見え方は実画像と区別する。（#124、44915823020、44919879164）
- Swiftがない環境で検査全体の成功だけを読む → `swiftc --version` を確認し、変更したコードに対応するSwift検査がskipされていないことを結果から確かめる。（#119〜121の配布検査）
- 画面外の`firstMatch`を直接読む → IDから現在の実候補を探し、元の上限内でスクロールする。（N97/N181）
- 手動訂正のスクロール対象を実要素だけで渡す → ID・ボタンの正確なラベル・候補条件のいずれかも指定する。どれもない呼出しはスクロールを始める前に失敗させる。（#205）
- 文字列やAnyで全画面を検索する → 実List・型・専用ID・実labelで絞る。QA状態は専用containerへ絞り、本文の前面に重ねない。（N173/N183/N189/N233/N238）
- スクロール前のnative identityを使い続ける → 接触直前に取得し、一意性・完全包含・enabled/hittableを確認する。長押しするTextも同じ。（N94/N97/N237）
- 仮想化される候補をすべてnative identityに結び付けてから枠を読む → 現在の実Listのsnapshotで枠を選び、完全に見えている候補だけを正確なIDから実要素に結び付ける。接触前に型・ラベル・枠・操作可能性を照合する。（PR #238）
- 確認・プレビューの待機で、読んだ状態ラベルをnative identityへ結び付け直す → 1回のsnapshotで専用container・状態ラベルの型とID・一意性・値まで確認する。期限と後続の実画面・実操作・保存の検査を維持する。（PR #238、ジョブ140453704352）
- 訂正の送信でXCTestのTap返却だけを確認する → 実ボタンのID・ラベル・可視枠・有効性・操作可能性を取得して一回だけ物理接触し、送信の結果が確認画面に現れるまで検査する。アプリへの配送と、到達後の状態取得はログで区別する。（PR #238、ジョブ140470113897）
- 同じframe/labelを何度も読む → 一試行の値を再利用し、現在のhittabilityは別に確認する。確認ボタンをタッチする直前の未選択は、同じボタンの実枠・識別子を取ったsnapshotから確かめる。（N165/N168/N174、44633231836）
- ファイル選択が戻った後にNavigationBar・TabBar・Listの枠を個別に照会する → 同じsnapshotで現在表示されている各要素の型・識別子・一意性と利用できる範囲を確認し、スクロール後に取り直す。元の戻り先・実ボタン・実取消は検査する。（PR #238、ジョブ140453704458）
- 一意な授業カードの枠を取得した後、別のタップ位置照会で止まる → 目的が授業詳細を開くことなら、同じsnapshotの完全に見えている有効なButtonの中央に実接触を一回送る。元の期限内に正しい詳細が開くことを必須にする。（44700448423試行4、44734888974）
- 検査済みCellの子を再列挙する → 同じ試行の実子・枠を保持し、dragは操作部品を避ける。（N78/N80）
- tapの返却を成功とする → 実値・Binding・保存と全callerの配送を確認する。接触時間・取消は実記録から対処し、押し直し・注入・期限延長で救済しない。（U64/N180/N192/N212/N239）
- ドラッグの始点を送出時に再照会する → その場で見た対象の一意な実枠を保持し、同じアプリ座標系で始点と終点を作る。閉鎖は詳細の実消失と元画面の実表示まで確認する。（N117、正式44527990308）
- 送出側の時刻をタッチ時刻とみなす → 実アプリが受け取った開始・終了・取消と演出段階を記録する。連続ドラッグの判定は実受信と実到着を使う。（#122）
- 選択失敗と画面情報の取得失敗を同じ原因として扱う → 実接触の配送、アプリの実選択、照会が戻ったかを個別に確認する。例えば44622550899では実照合と確定可否が成立した後、架空操作の全画面照会で止まった。（N187、U63）
- 論理的な到着を描画の完了として扱う → 実画面の枠、表示時刻、方向、上下位置を観測する。表示の停止があれば、アプリのメインスレッドの処理時間と表示コールバック間隔を照合する。（#118、正式44527990308）
- 実枠の採取中に別用途の診断を組み立てる → 画面の枠は元どおり採取し、検査の後半だけで使う診断JSONは採取後に生成する。週送りでは採取中の診断呼び出しが0件であることも確認する。（正式528、限定45149532016）
- 無条件でHomeを送る → SpringBoardが既に前面なら重ねない。元の準備条件・一回launchを守る。（N179/N182）
- Runtime登録直後に取得物を消す → test/device回収後まで保持し、最後のalwaysで所有領域だけ消す。（N176/N177）
- bootstatusのFinishedだけで実UIの開始を判断する → 次のコマンドと所有Simulatorの状態も確認する。開始前のShutdownは環境側の失敗として記録し、アプリ側の操作結果は未検証とする。（N194/N198）
- 終了コードだけを見て時間切れと判断する → 準備・起動・XCTest開始・実検査・清掃の時刻を、個別の期限とジョブ全体の期限に照らす。同じiOS26単項目にも実操作前の合計枠終了と、実接触後の画面照会失敗の両方がある。（44616414594、44622550899）
- shutdown失敗を一律無視する → exit149だけ、正確な所有UUID/Runtimeが一意なShutdownと実確認した場合に受理する。（N170）
- APIの返却・途中状態だけで成否を決める → 元の期限内で実状態・所有回収を確認し、timeoutは失敗にする。（N162/N188/N224/N234）
- helperと別callerのmockを別々に直す → 全caller/mockを検索し、実JSONへ揃える。一時領域は入力ごとに分離・回収する。（N178/N229）
- 全device一覧やログ名の想定で証明する → 実RunnerのID・OS・Simulator条件を照合し、テスト名は実classで正規化する。（N07/N199/N200/N211）
- テストの警告で失敗用の撮影を消費する → XCTestが実際に試験の失敗と判定する `isFailure` を参照し、全てのissueを通常どおりXCTestへ渡す。（PR #238、ジョブ140523988502）
- iOS Simulatorを起動するCIでは、失敗を検出した時点で、シャットダウン前にジョブが作成した架空データ用の端末を最大1枚撮る。通常UI、手動訂正、ファイル選択ではXCTestが失敗を記録する時点を優先する。その画像を取得できなかった場合とOCRの2種類のiOS実行では、同じ終了時の処理を使う。終了時の撮影は15秒、PNGは2 MiBを上限とする。長辺1024px以下へ縮小し、終了時の画像で変換が必要な場合は5秒以内に処理する。復元に必要なデータとSHA-256をジョブログの `TAKUPOKE_UI_IMAGE` に残す。外部からの取消では撮影を待たず端末の回収へ進む。成功時と端末未作成時の診断撮影や、ファイルの別途アップロードは行わない。端末が応答せず撮影できない場合も元のテスト結果を保持する。画像は失敗検出後の画面で、画面遷移や終了が先行した場合は、失敗した操作の瞬間とは異なることがある。
- 部分成功で公開する → 同じsource/run/attemptの全15必須成功を要求する。毎回の新規review・残job確認・未実機確認の明記も守る。

個別成功を恒常的な解消へ一般化しない。詳しい手順は[テスト保守方針](test-maintenance-policy.md)へ。
