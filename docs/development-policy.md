# 確定した開発方針

この文書を iOS 版の実装判断の基準とします。方針を変更するときは、実装とともに文書も更新します。

未確定の解析規則や利用者に見える振る舞いは、開発者の判断だけで仕様化しません。既存仕様から決まらない点は、具体例と利用上の影響を平易に説明して利用者へ確認します。確定済みの仕様や通常の実装方法について、繰り返し承認を求めることはしません。

## アプリの構成

- iOS ネイティブアプリとして新規開発する。
- 言語は Swift、UI は SwiftUI を採用する。必要な箇所のみ UIKit を併用する。
- 既存の `takupoke-astro` をラップする方式は採用しない。
- Web 版とは別実装とし、必要なデータ仕様・解析ルールのみ合わせる。
- Windows 版は今回の開発対象に含めない。Windows とのコード共有のために iOS 版を複雑化しない。

## 新規UIのデザイン

- 今後追加する画面・操作部分にはApple標準のLiquid Glassを採用する。既存画面の全面的な置き換えは後の作業とする。
- SwiftUIの標準ナビゲーション・ツールバー・ボタンなどを優先する。独自の操作部品で必要な場合に `glassEffect` / `GlassEffectContainer` を使用する。
- 時間割の文字や資料本文の読みやすさを確保し、ガラス表現は主に操作・ナビゲーションの層に適用する。アクセシビリティの透明度・動きの設定も尊重する。
- Liquid Glassを使う新規UIに合わせ、ActionsはXcode 26.3を使用する。iOS 26 SDKによるビルド・実機の確認状況は検証記録で管理する。
- 現行のiOS 16以降という最低対応条件は維持する。iOS 26以降ではLiquid Glassを利用し、それより古いOSでは利用可能な標準SwiftUI部品へ分岐する。
- SDK更新に伴う既存標準部品の外観変化と、既存画面を作り直す作業は区別して検証する。

参照: [Apple: Adopting Liquid Glass](https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass)、[Applying Liquid Glass to custom views](https://developer.apple.com/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views)。

## 学校資料へのアクセス

- Microsoft Graph は使用しない。
- 学校側の権限制約を避けるため、iOS 標準の「ファイル」から OneDrive File Provider 経由でアクセスする。
- 対象資料は通常時間割 PDF、学校行事 PDF、時間割変更 XLSX とする。
- 通常時間割・時間割変更は「ファイル」経由とする。学校行事は利用者指定の学校公式の固定PDF URLから取得する。
- 学校行事PDFは端末内に保持し、起動のたびに再取得しない。手動更新時はETag / Last-Modifiedで変更を確認し、未変更ならPDF本体の再取得を省く。
- 学校行事は利用者が別途API化を検討するため、次の明示的な指定まで既存の取得・解析・タグ・表示を変更しない。今回相談した追加タグや集中講義の再分類は未反映とする。APIの接続先・仕様は未定で、先行して移行しない。
- 学校サーバーに負荷をかけないため、CI・自動テストでは本番URLへ通信しない。HEADや疎通確認も対象とし、架空URL・応答で検証する。実装に必要な調査としての取得は許可済みで、必要な回数に限定する。アプリの通信は利用者の取得・更新操作時に限定する。
- フォルダ選択は対応サービスで利用できる構成を維持する。OneDriveでは利用者の実機でフォルダ選択ができなかったため、個別ファイル選択を基本とする。継続アクセスはブックマークで管理する。
- フォルダ選択や継続アクセスの可否は実際の OneDrive File Provider と実機で検証する。成立しない場合のファイル単位選択・再選択手順も検討する。
- アクセス許可やファイルの可用性を保証済みと扱わず、取得できない場合は既存データを保持し、状態を利用者へ示す。

## 解析

### PDF

- PDFKit を使用する。
- 学校の実際の書式に特化した解析処理を実装する。
- 曖昧な内容を推測で時間割へ反映しない。未解析・曖昧・失敗を正常な解析結果と区別して管理する。
- 実資料の検証は非公開の環境で行い、公開テストには架空の資料を使用する。
- 並記された授業の対応付けと教室名の変換順序は [PDF解析の仕様確認](pdf-specification.md) に従う。教室の空欄を保持して授業ごとに分割した後、確認済みの対応表で正式名に変換する。
- 科目・教員・教室のPDF記載名と正式名称を別々に保持し、どちらも表示に使えるようにする。Web版と同じく一覧では短い記載名、詳細では正式名称を優先し、正式名称がなければ記載名を使う。

### XLSX

- Swift で解析する。
- 既存の `denpa-schedule-csv` の仕様を確認し、日付正規化、クラス展開、変更前後科目、教員、教室、備考などの仕様を移植する。
- 既存実装との結果比較をテストに使用する。
- 比較に使う入力・期待結果のうち、公開リポジトリや公開 CI に含めるものは完全に架空のデータとする。実際の教師名・教科名は使用せず、「架空教員A」「架空科目A」などを使う。実資料の名前だけを置き換えたデータも使わない。
- XLSXのZIP展開にはコミットを固定したZIPFoundation、XML読み取りにはXMLParserを使用する。解析規則・上限・互換性の差異は [XLSX移植仕様](xlsx-specification.md) に記録する。

## 端末内の統合・保存

- 通常時間割・学校行事・時間割変更を端末内で統合する。
- iOS 版は `denpa-schedule-notifier` なしで動作させる。
- データは端末内に保存する。
- 開発版のSQLite切替では旧JSONのデータ移行を必須にしない。資料を再取得・再解析して新DBへ保存し直す方式を採用し、移行処理の追加・アプリへの接続は当面行わない。この切替方針と、通常更新の失敗時に正常データを保持する方針は区別する。
- 元ファイルの状態、最終更新日時、解析結果、時間割変更などを管理する。
- 元ファイルの更新日時、最終取得成功日時、最終解析成功日時、更新試行の結果は区別して扱う。
- 取得・解析・検証を完了してから正常データへ反映する。途中の失敗で正常な既存データを破壊しない。
- ファイル更新時は再取得・再解析し、差分を時間割へ反映する。
- 取得や解析に失敗した場合は前回正常データを維持し、更新失敗を明示する。
- 保存方式、統合の優先順位、差分の識別方法などの詳細は、仕様確認と検証に基づいて決定する。

## 一時ファイルの管理

- このデバイス・Windows の開発環境と iOS アプリの端末内で、ローカルに一時ファイルを溜めない。
- ダウンロード途中のファイル、展開物、解析用コピー、検証用の出力などは、用途を限定した一時ディレクトリに作成する。
- 不要になった一時ファイルは処理終了時に削除する。失敗・キャンセル時にも可能な範囲で削除し、異常終了で残ったものは次回起動・実行時に回収する。
- 削除はその処理が所有する一時ファイルに限定し、実行中の別処理のファイルを削除しない。
- 元資料、継続利用に必要な保存データ、前回正常データは一時ファイルと区別し、後片付けで削除しない。
- Git の除外設定だけで済ませず、開発作業で作成した一時ファイルも作業完了時に片付ける。

## 開発・配布・更新

- 開発環境はこのデバイスと Windows の両方とする。
- GitHub へ push し、GitHub Actions の macOS runner で iOS をビルドする。
- Mac 所有は前提にしない。
- AltStore Classic による実機導入を前提とする。
- AltStore Source は最初のステップで必ず構築する。
- GitHub Actions で IPA を生成・公開し、バージョン / build 番号と Source JSON も自動更新する。
- iPhone では AltStore Source から初回導入・アップデートできる状態を最初に完成させる。
- アップデート機構は必須機能とする。
- 通常の開発フローを「このデバイスまたは Windows で編集 → GitHub push → Actions で IPA 生成 → AltStore Source 更新 → iPhone で更新」に固定する。
- ビルド、IPA 公開、Source 更新の整合性を保ち、失敗したリリースを有効な更新として案内しない。
- Actions のキャッシュ・保存用 artifact を使用せず、容量枠を手動管理する運用を避ける。ビルドから Release 公開までは同じジョブで完結させる。
- GitHub Releases の正式な配布物はキャッシュ・artifact とは別に扱い、件数制限による自動削除は行わない。
- 配布 URL、Bundle ID、バージョン規則、署名・導入手順、Source の具体的な形式はステップ①で確定し、実機の結果を記録する。

## 通知・バックグラウンド更新

- 通知は UserNotifications を使用する。
- バックグラウンド更新は BackgroundTasks を使用する。
- 起動時・復帰時・手動更新を基本とする。
- バックグラウンド実行は実機で確認できた範囲だけ仕様化する。未検証の実行頻度や定時更新を保証しない。

## 公開リポジトリ

- 公開リポジトリにできる構成を維持する。
- 学校の実資料、抽出結果、個人情報、メールアドレス、認証情報を公開物へ混入させない。
- Git の作者・コミッターのメールアドレスには GitHub の非公開用 `noreply` アドレスを使い、個人・学校のメールアドレスを公開しない。両方の開発環境でリポジトリごとに設定する。
- Git のコミット作者情報、Actions のログ、IPA、Release 添付、Source JSON も確認対象とする。
- 詳細は [公開リポジトリでの情報管理](public-repository.md) に従う。
