# CIの実行時間

アプリUIはiOS 26・27で検証し、配布ビルドと公開を同じRunnerで行います。処理の実行順とテストの準備を改善し、必要な検証を維持したまま所要時間を短縮します。

## 計測

`tools/timed_command.py`が各処理の開始・終了と経過秒数を出力します。対象はテスト用プロジェクト生成、シミュレーター起動、UI検証、保存・取得の検証用コンパイルと実行、Swiftパッケージのテスト、iPhone向けReleaseビルドです。ReleaseビルドはXcodeのBuild Timing Summaryも出力します。

同じ配布Runner内では、ファイル選択UIが成功した後にホストテスト・ビルドを実行します。234ではシミュレーター起動に約357秒、保存テストのコンパイルに約456秒かかり、標準ファイル画面のキャンセルボタンを取得できませんでした。負荷との因果関係は未確定ですが、シミュレーターとSwiftコンパイルの競合を避けます。ピッカーのビルドも実行するシミュレーターのアーキテクチャに限定します。`tools/parallel_build.py`は処理名を付けたログを実行中に出力し、中止・失敗時には起動したプロセス群を停止します。各処理の一時ファイルは片付けます。

## 実行順と公開条件

配布テストの成功後、Native PDF・復旧、iOS 26・27それぞれの通常UI2組、
各OSの手動訂正3ケースを並行して開始します。
全12検査が成功してから配布ビルドを開始する依存関係へ変更しました。
いずれかが失敗した場合、配布ジョブは開始しません。検査待ちのためのRunner占有を避けます。
IPAは公開までRunner内に保持します。保存用artifact・Actionsキャッシュは使用しません。

`tools/release_gate.py`は、現在の実行ID・再実行回・コミットに対応する
配布検査、Native、通常UI4ジョブ、手動訂正6ジョブの計12チェックを確認します。
公開ジョブ自身の完了は待ちません。必要なジョブの失敗・中止・スキップ、
異なるコミットや再実行回、重複ジョブ、APIエラーを検出した場合は停止します。
未完了・未登録のジョブは60秒間隔で最大40分待ち、時間切れなら停止します。
mainのコミットと公開物の照合は公開処理でも行います。

開発ブランチではPythonとportable Swiftを並列に実行し、必要な画面は
登録済みケースだけを選ぶ診断workflowで両OSを検証できます。
この結果は配布前の全検証に代用しません。mainの通常公開経路と公開ゲートは維持しています。

UIテストは最初から各テストに必要な条件で起動します。文字サイズ・空データ・更新・取得失敗の確認で、標準条件のアプリを起動してから直ちに起動し直す処理を省きます。設定の保存や通知の差分確認に必要な再起動はテストに含めます。

## UI検証の分割

`tools/ui_test_manifest.py`の通常画面27項目をAの15項目・Bの12項目に分け、
各OSの別Runnerで実行します。文字サイズのOS設定3パターンはB組で追加実行します。
iOS 26のVoiceOver操作だけは従来どおり対象外で、iOS 27では実行します。
手動訂正3項目は各OSの別3ジョブで実行します。分割表は現在の登録数であり、
下の旧版の測定では18項目でした。現在の全体時間は下の347の測定に記載します。

ソースに宣言されたテストと分割表を照合し、追加漏れ・古い項目・重複を検出した場合は停止します。XCTestの完了ログも選択した項目と照合し、未実行・重複・失敗・想定外のスキップを検出した場合は失敗とします。公開には両OSのA・B、計4ジョブの成功を必要とします。分割指定なしのローカル実行では全項目を実行します。

通常UI用4台、手動訂正用6台、Native用1台、配布用1台を使用します。
各Runner内のシミュレーターは1台に限定します。分割によってコンパイルと
依存関係の取得は増え、開始待ちも全体時間に影響します。
同一ジョブの手動訂正はbuild-for-testing後のtest-without-buildingで準備を再利用します。
重いケースの単純な直列化はせず、所要時間と使用時間を実測して配分を検討します。
